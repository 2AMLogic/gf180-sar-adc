## 5. Full corner verification vs a ratified spec — **FAIL, on three rows**

governing verdicts are:

### 5a. ENOB @ Nyquist — FAIL (governing extracted side)

- Target `> 9.0` bits. **Measured 8.857 bits worst** (`tt_125c_3.63v`),
  below target at **2 of 9** grid points (`tt_125c_3.63v` 8.857,
  `ss_125c_2.97v` 8.969).
- Governing record:
  [`sim/adc-enob-fft/records/20260817-215657-076d545.md`](adc-enob-fft/records/20260817-215657-076d545.md)
  (extracted, against the current post-#215/#223 layout; issue #224),
  adjudicated in `sim/extracted-delta-summary.md` §4.13.2.
- Schematic side also fails: 8.5064 bits worst (`ss_125c_2.97v`).
- **This is a regression introduced by DR-0019's ratified CDAC resize.**
  Pre-resize the extracted row read 9.103 bits and PASSED.
- Mechanism isolated (#211, `sim/dr0019-cu-sweep-findings.md`): the loss
  tracks the acquisition time constant `R_on·C_arr`; an orthogonal control
  widening only the CDAC cell's fourth-leg acquisition T-gate recovers
  9.170 bits worst-corner, clearing `> 9.0` at all nine points. That control
  is explicitly **not** a proposed design — §4 of that document lists five
  quantities (charge injection, top-plate `C_par`, comparator kickback,
  clock-driver power, area/routing) it deliberately did not measure.

### 5b. SFDR @ Nyquist — FAIL (governing extracted side)

### 5d. Finding: PR #232's merge does **not** constitute ratification of DR-0024

Issue #236 asked this pass to resolve, rather than assume, whether the
operator's 2026-08-21 merge of PR #232 is itself the ratification act for
DR-0024 under `2AMLogic/2am#357`'s Class 1 standing policy. **It is not.**
Three independent findings, each checked directly:

1. **Merge attribution to `rjwalters` carries no ratification signal in this
   repo.** `gh pr list --state merged` shows `rjwalters` as `mergedBy` on
   roughly half of *all* merged PRs here, including purely mechanical ones —
   PR #163 ("remove three unused helpers"), PR #199 ("dedupe `_klt_version()`
   into `klt_env.py`"), PR #201 ("dedupe `compose_dc_deck()`"). The operator's
   token is the ordinary Champion auto-merge credential in this repo, so a
   merge under it is **indistinguishable from a routine automated merge** and
   cannot be read as a deliberate approval act.
2. **The timeline is the ordinary automated pipeline, start to finish.**
   `gh api .../issues/232/timeline`: `labeled loom:review-requested`
   06:11:33Z → bot Judge `commented` ("Judge review: **approve**") 06:15:27Z →
   `labeled loom:pr` / `unlabeled` 06:15:28Z → `merged` 06:15:52Z, **24
   seconds** after the bot's label swap. `gh pr view 232 --json reviews`
   returns `[]` — **zero** GitHub reviews of any state. The PR never carried
   `loom:operator`, which is the hold label the fleet uses precisely to stop
   an automated merge of a ratification PR (see `sky130-pll#19`/PR #53, where
   `loom:operator` is deliberately re-applied and a sweep declines to merge:
   *"merging that PR is itself the ratification act"* — the mechanism assumes
   a **held** PR the operator merges by hand, which #232 never was).
3. **The Class-1 "operator-approval-as-ratification" policy had already been
   superseded when #232 merged.** Epic `2AMLogic/2am#372` — *"autonomous spec
   ratification — two-key (EE + market) release **replaces**
   operator-approval-as-ratification"* — was operator-ruled **2026-08-20**,
   the day before. The operator's own comment on issue #198
   (2026-08-21T05:58:45Z, **17 minutes before #232 merged**) says so
   explicitly: *"The two-key release mechanism (EE key + market key,
   `RATIFY-KEY` markers, `loom:auto-merge-ok`) is live: the protocol shipped
   in 2am#383/#387/#390."* Under that protocol the ratification act is two
   `RATIFY-KEY` marker reviews, neither held by the PR's or design's author
   (`2am#390`), followed by `loom:auto-merge-ok` plus a consolidated
   ratification-record comment. **PR #232 has none of these**: no
   `RATIFY-KEY` marker anywhere in its comments or reviews, no
   `loom:auto-merge-ok`, no consolidated ratification-record comment; its
   only label is `loom:pr`.

**And DR-0024 is squarely inside that protocol's strictest branch.** The same
operator comment states: *"For any row here that is a
**relax-after-measured-FAIL** (a proposed value weaker than a previously
ratified one …): the PR path still applies — the market key must explicitly
find the relaxed value competitive against named public parts, and escalates
`loom:operator` if it cannot."* DR-0024 revises a ratified `< 0.1 mm²` to a
weaker `< 0.16 mm²` after a measured miss — the definition of a
relax-after-measured-FAIL. So the required bar is not merely two keys but a
market key with an **explicit competitiveness finding**.

**Blocking infrastructure, checked directly**: the Tier-1-clean ratification
reviewer variant that 2am#372's own success criteria require to be *"installed
in every canary repo with a ratification PR in flight"* is **not installed
here** — `.claude/skills/` at `7699317` contains only `repo`, and
`grep -ril RATIFY-KEY` over the tree returns nothing.

**Consequence for this pass**: DR-0024's `Status: proposed` is **correct as
written**, and `README.md`'s Area row correctly still reads `< 0.1 mm²`.
Neither field is flipped by this change. The specific remaining ask is filed
as its own operator-gated follow-up rather than assumed either way, per
#236's own acceptance criterion (b). The same finding applies verbatim to
**DR-0023** (`Status: proposed`, merged the same way by PR #230 on
2026-08-19) — noted here because it is the same defect, not folded into the
Area finding.
