## Why this record exists

Issue #958 adds a fourth job, `klt-parasitics`, to
`.github/workflows/nightly-pdk.yml` so that
`layout/adc-top/parasitics/run_extract_parasitics.py --check` runs against
the pinned `klt` and the pinned gf180mcuD PDK every night, and documents that
runner in `.github/workflows/ci.yml`'s "INVENTORY OF SELF-CHECKS" comment
block (the issue's acceptance criteria name both files).

`.github/workflows/ci.yml` is one of the five paths T1 item 10's inventory
(`signoff/repo-hygiene-inventory.json`) attests by sha256, so a comment-only
edit to it still moves the pinned hash: `086a222eee36564d…` (what the
superseded record attested) to `5832363526e55101…`. CI's
`signoff/run_signoff.py --check` failed on the branch with four problems,
the same two on each partition — the `ci.yml` hash in the envelope no longer
matching the committed bytes, and the envelope's attested hash no longer
matching `freshness.json`'s pin. Everything else was green.

Per `signoff/README.md` "Changing the verdict" step 2, `--regen` does not
re-mint the item-10 envelope; the hand re-attestation is owed "whenever a
file one of those inventories names has changed — not only when the
inventory itself has." Done under the pinned grader, from the repo root:

```bash
klt signoff --attest 10 --inventory signoff/repo-hygiene-inventory.json \
  --format json -o signoff/repo-hygiene.envelope.json
python3 signoff/run_signoff.py --regen --klt <the pinned klt>
```

The re-attestation passed 9/9 checks. Its four `command` checks re-ran
against the tree carrying the #958 change — the harness unit tests
(`test_harness.py`), `python3 -m compileall -q sim layout design signoff`,
`sim/tools/check_markdown_links.py` and
`sim/tools/check_characterization_summary.py` — all exit 0. No item-9 input
changed in this change, so the item-9 envelopes were not re-attested.
`--regen` re-attested items 1 and 2; their envelopes and the manifest are
byte-unchanged (they do not appear in the change at all).

**Disclosure — the repo-root `README.md` hash in this envelope.** The
re-attestation also refreshed the envelope's recorded hash of the repo-root
`README.md`, from `753fa2f89ebb1ec1…` to `a3006433493f7de7…`. That is not a
`README.md` change of this issue: the superseded envelope's hash was already
stale on `main` by design, because step 4 of "Changing the verdict" re-points
the root README's current-record citation *after* every regen and
`run_signoff.py --check` exempts `README_CURRENT_RECORD_FILES` from the
hash comparison. It lags again now, for the same reason, after this record's
own citation was re-pointed.

**Disclosure — what this attestation does not cover.**

lives, is **not** in item 10's inventory and is not attested by anything
