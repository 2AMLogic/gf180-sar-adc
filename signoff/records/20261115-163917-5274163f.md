## Why this record exists

PR #826's review found the regression gate this branch adds was defined but
never executed: `package.json` declared `check:lvs-requests` while `check:ci` —
the only chain CI runs — did not include it, so the INVENTORY comment this
branch added to `.github/workflows/ci.yml` claimed "RUNS HERE" for a gate that
did not run there. The fix wires the gate into `check:ci` (it now runs between
`check:signoff` and `report:evidence-footprint`), and extends the gate itself
so the two writer surfaces the review flagged are covered:

- every committed `*.ref.spice` header must document exactly one
  `klt lvs <path> --format json` invocation resolving to its sibling
  `<stem>.lvs.json` (all 23 committed files carry one and pass; the header
  writer sites were previously unguarded);
- a `*.lvs.json` that is neither a request document (`_comment`) nor a
  recognizable report (a report-only key: `schema_version`, `status`,
  `engine`) now fails instead of being silently skipped — the discriminator
  is deliberately NOT `layout`/`reference`, which every committed report
  also carries.

Updating the INVENTORY comment for that extended coverage edited
`.github/workflows/ci.yml` again, and that file is named in
`signoff/repo-hygiene-inventory.json`'s `hygiene` list: `klt signoff --attest
10` pins its bytes and `run_signoff.py --check` re-hashes them on every pull
request (`sha256:b412ff84…` pinned vs `sha256:086a222e…` committed), so the
envelope had to be re-minted and the report re-recorded — the same drift the
previous record documented.

The other files this change touches (`package.json`, the check
`sim/tools/check_lvs_request_invocations.py`, its negative-control test) are
**not** inventoried by item 10 and pin no hash here.

**The `README.md` hash in the envelope moved for the same designed lag the
previous record documented.** `README.md` is inventoried by item 10, but step 4
of `signoff/README.md`'s "Changing the verdict" re-points its
`signoff:current-record` citation *after* the record id exists — so every mint
records the pre-re-point bytes. The `f2227a70…` -> `6fc0b23e…` move above is
the previous record's re-point being picked up by this mint, and this
record's own re-point moves it again. That lag is deliberate and declared:
`README.md` is exempt from `--check`'s envelope re-hash and from
`freshness.json`'s `artifacts` pins alike, for precisely this reason.

**No manifest citation and no pinned `content_hash` in

(`signoff/repo-hygiene-inventory.json`), whose bytes this
change does not touch — only the envelope the inventory attests. Both
partitions (`10.analog`, `10.digital`) cite that one shared envelope, which is
why one workflow-comment edit reported four problems.

  pull request. The inventory deliberately excludes every check that reads
