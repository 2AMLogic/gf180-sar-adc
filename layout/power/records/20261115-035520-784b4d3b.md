# Power spec schema record 20261115-035520-784b4d3b

Append-only record, but not a run record: no `klt power` solve was minted here.
This is the schema-compatibility record issue #799 (part of #652) asks for —
what the newer `klt` requires of the committed power specs, where each
forbidden key's information goes under it, and every pin or hash that moves
when the specs are edited, so #652 can sequence the pin bump against its
evidence regeneration. Everything below was reproduced in a throwaway
environment (`uvx --from "klayout-tools==0.8.0"`); no host tool was installed
and no repo file was modified to produce it.

- **Record ID** — `20261115-035520-784b4d3b`
- **Claim** — `klt power` at 0.8.0 rejects the committed power specs' nine
  underscore provenance keys (three names, two sections) as unknown fields,
  reporting them one entry per run; every key's information has a supported
  destination under 0.8.0 (`_comment`, and `current_limit_source` for the
  absent-limit rationale), with the loss being structure, not content; and the
  only hash/equality surface a spec edit moves is `--verify`'s recomposition
  equality against the 13 committed snapshots — `signoff/` pins nothing from
  `layout/power/`.
- **Not claimed** — anything about a 0.8.0 solve. No IR-drop or EM number in
  this record; re-deriving those is #652's job, not this one's.

```

'stackup[0]._sheet_resistance_source' -- this klt does not recognise it (allowed here:
current_limit_a_per_um, current_limit_source, label_layer, layer, name,
sheet_resistance_ohm_per_sq, plus the '_comment' annotation); a misspelt key, a key from
a newer klt release, or a key that belongs to a different section
```

(line-wrapped for this record; content otherwise exactly as printed. `…`-style
elision: none — the spec name is the scratch copy's.)

Stripping `stackup[0]`'s two underscore keys and re-running surfaces the next
section:

```
klt power: spec 'spec.nostack.json': unknown fields 'vias[0]._current_limit_absent',
'vias[0]._resistance_source' -- this klt does not recognise it (allowed here: between,
current_limit_a, current_limit_source, cut_size_um, cut_space_um, layer, name,
resistance_ohm, plus the '_comment' annotation); a misspelt key, a key from a newer
klt release, or a key that belongs to a different section
```

Stripping `vias[0]`'s keys too names the **next entry**, not the rest of the
section — the gate reports one offending entry per run:

```
klt power: spec 'spec.novias0.json': unknown field 'vias[1]._resistance_source' -- this
klt does not recognise it (allowed here: between, current_limit_a, current_limit_source,
```

So the 2026-10-27 Builder note on #652 ("`_current_limit_absent` and
`_sheet_resistance_source` stackup keys") was the **first error only**. With
every underscore key stripped from both sections the gate is clear — the next
failure is downstream of spec validation:

```
klt power: could not read layout 'stub.gds': Stream has unknown format: stub.gds in Layout.read
```

## The nine keys, and where each one goes

Enumerated from `adc_block.power-spec.json` (identically present in all 13
snapshots of `reports/20261106-202719-e38687e0/`, verified by grep): nine keys,
three names, two sections.

| Path | Key | Carries (today) | Destination under 0.8.0 | Verified |
|---|---|---|---|---|
| `stackup[0]` (Poly2) | `_sheet_resistance_source` | where 7.3 Ω/sq came from: `gf180mcuD.tech` `resist (allpolynonres)/active 7300`, variants nominal, foundry doc | `_comment` only — `sheet_resistance_source` as a field is rejected (see below) | yes |
| `stackup[0]` (Poly2) | `_current_limit_absent` | why no limit exists: no `DCCURRENTDENSITY` for Poly2 anywhere in the install, edges reported unchecked | `current_limit_source` field (first-class, accepted even with no limit beside it), or `_comment` | yes |
| `stackup[1]` (Metal1) | `_sheet_resistance_source` | where 0.090 Ω/sq came from: tech `resist (allm1)` cross-checked against the tech LEF `RESISTANCE RPERSQ` | `_comment` only — same rejection | yes |
| `vias[0]` (Contact) | `_resistance_source` | where 8.0 mΩ came from: `contact pc 8000`, variants nominal | `_comment` only — `resistance_source` as a field is rejected (see below) | yes |
| `vias[0]` (Contact) | `_current_limit_absent` | no `DCCURRENTDENSITY` for CON (33/0) | `current_limit_source` field, or `_comment` | yes |
| `vias[1..4]` (Via1–Via4) | `_resistance_source` | where each 4.5 mΩ came from: `contact m2c/m3c/via3/via4 4500` | `_comment` only — same rejection | yes |

The top-level `_comment` is **not** affected: `compose_spec`
(`run_power.py`) pops it before the spec ever reaches `klt`, which is exactly
why the per-entry underscore keys are the ones that do reach it.

Destinations were verified by rewriting the spec, not read off the allow-list:

- every entry's underscore keys folded into that entry's `_comment` — gate
  clears (failure moves to the stub layout read);
- `_current_limit_absent` rewritten into `current_limit_source` (Poly2 and
  Contact, neither carrying a limit) — gate clears the same way;
- `sheet_resistance_source` as a stackup field — **rejected**:
  `unknown field 'stackup[0].sheet_resistance_source'` with the same
  allow-list as above;
- `resistance_source` as a vias field — **rejected**:
  `unknown field 'vias[0].resistance_source'` with the vias allow-list.

So nothing is lost but structure: all nine keys' content survives verbatim in
`_comment`, and the absent-limit rationale even gains a first-class field —
but sheet- and via-resistance provenance has no machine-readable home, while
current-limit provenance does. That asymmetry is filed upstream as
[klayout-tools#5791](https://github.com/2AMLogic/klayout-tools/issues/5791)
(ask: a `sheet_resistance_source`/`resistance_source` counterpart to
`current_limit_source`; secondary note there: the gate's one-entry-per-run
reporting). Until it lands, `_comment` is the only destination for seven of
the nine keys.

## What moves when the specs are edited

The AC asked for "every pin or hash that changes". Verified against
`origin/main` @ `784b4d3b`, the honest answer is that most of the named
surface does **not** move:

| Surface | Moves? | Evidence |
|---|---|---|
| `signoff/freshness.json` | **No** | carries no hash of any `layout/power` path (grep for `"layout/power…": "sha256` → nothing); its only `layout/power` string is prose in `citations/11.analog/parts[0].note` naming a **record** (`records/20260923-084734-5f13cf9.md`). Contrast: the ERC spec **is** hashed (`layout/erc/adc_block.supply-spec.json` → `sha256:bc7482…`), which is probably what suggested otherwise |
| `signoff/gf180-sar-adc.manifest.json` | **No** | zero `layout/power` references |
| `cases.json` `layout_sha256` | **No** | pins the GDS, which a spec edit does not touch |
| `layout/power/reports/20261106-202719-e38687e0/` (13 composed specs) | **Yes** | `check:power` is `run_power.py --verify`: it re-composes every case from `adc_block.power-spec.json` + `cases.json` and fails on `recomposed != committed_spec`. All 13 committed snapshots carry the nine keys (13/13 verified), so **any** base-spec edit — including merely deleting an underscore key — fails `check:power` with no `klt` involved, until this report directory is regenerated |
| `layout/power/toolchain.json` | **Yes** (with the bump, #652's half) | `klt_version` `0.6.0`→`0.8.0`, `klt_git_commit` `c622e8ad…`→`c572046b…`, `klt_git_tag` `v0.6.0`→`v0.8.0`, `klt_install` `klayout-tools==0.6.0`→`==0.8.0`, `klayout_package` `0.30.10`→0.8.0's expected `0.30.12` (note: 0.8.0's own constraint is `klayout>=0.30` and the scratch env resolved `0.30.13` — the pin must be chosen deliberately, and `resolve_klt` asserts the resolved value against it) |
| `layout/power/README.md` install prose | **Yes** (with the bump) | the "Install and run" section quotes the 0.6.0 git-commit install line and the 0.30.10 klayout pin |
| `layout/power/records/` | **Yes** | append-only: the re-run mints a new record; the 0.6.0 records stay |

**The sequencing fact #652 needs:** the schema edit, the `toolchain.json`
bump, and a regenerated `reports/<new-id>/` directory must land **together**
(one `run_power.py` re-run mints the reports and the record); a specs-only or
pin-only PR cannot exist, because `check:power` fails the moment the base spec
moves and committed reports are append-only evidence that this issue is
forbidden to touch. And the re-run's verdicts must be re-read case by case —
0.8.0's connectivity model is a newer klayout, and the committed droop numbers
are solved on the network, not the GDS.
