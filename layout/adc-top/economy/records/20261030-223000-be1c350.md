# Decode-bank folding experiment 20261030-223000-be1c350 — null result (issue #668)

Append-only evidence record. Question (issue #668, child of #644): does folding
the decode-bank devices into multi-finger devices recover the banks'
non-drawn bbox area (`decode_banks_total` = 30,139.2 µm² in `area.json`)?

**Answer: no. Folding as modelled here makes the block larger, not smaller.**
No ratified row was touched; no layout artifact in this change was regenerated.

## Part 1 — is device merge available? (AC-1)

klayout-tools#261 (LVS device merge) is closed (klayout-tools PR #274). The
capability is **opt-in**: `options.combine_devices` in the `klt lvs` request
(default `false`; every committed `*.lvs.json` omits it).

Flag-neutrality regression on the *unchanged* single-finger layout, flag on:

```bash
# copies of layout/adc-top/{adc_top,adc_block}.lvs.json + .spice/.ref.spice,
# with "options": {"combine_devices": true} added
klt lvs adc_block.on.json --format json   # status: match
klt lvs adc_top.on.json   --format json   # status: match
```

Both report `status: match` (only the pre-existing `device.geometry_not_compared`
warnings for the MiM caps / poly resistors). klt used: `klt 0.8.1.dev835+geae64ef5dc41`
(host install). **Not run** against the `signoff/toolchain.json` pin
(`44cc4232`, which carries the flag per `lvs.py`) or the `layout/toolchain.json`
pin (`klayout-tools==0.6.0`, which predates it, unchecked) — so the verdict above
is for the host build only.

## Part 2 — area experiment (AC-2)

The premise "folding could roughly halve the bank width" is backwards. A bank
column's X pitch is `2*SD_EXT + L + COLUMN_GAP` (`lib/geometry.py`)
regardless of `W`; the row's height is set by the widest device (the 20 µm
PMOS of the T-gates). Folding a device into N fingers divides its height by N
and **multiplies its X footprint by ~N**.

Experiment: a throw-away patch to `lib/place.draw_devices` splitting every MOS
device wider than a cap into the minimum number of equal parallel fingers
(each finger a separate single-gate device, same nets; no diffusion sharing, so
this *over*-states the width of a real shared-S/D fold). Generator run via
`python layout/adc-top/gen_adc_top.py --outdir <tmp>` (reproduces the committed
`area.json` areas exactly on an unpatched tree). Patch not kept.

| max finger W | decode bank (µm) | decode banks total (µm²) | `ADC_TOP` / `ADC_BLOCK` |
|---|---|---|---|
| none (committed) | 440.94 x 31.5 | 30,139.2 | 490.5 x 253.3 = 0.12426 mm² / 0.15183 mm² |
| 10 µm | not built (`ADC_BLOCK` strap-corridor assertion) | — | `ADC_TOP` 560.9 x 233.3 = **0.13086 mm²** |
| 7 µm | 858.2 x 18.2 | 31,265 | `ADC_BLOCK` 874.4 x 226.7 = 0.19819 mm² |
| 5 µm | 961.9 x 16.5 | 31,818 | `ADC_BLOCK` 978.1 x 223.3 = 0.21843 mm² |

Every folded point is larger than the baseline; the bank width grows faster
than its height falls, and the block width follows the bank. Shared S/D
diffusion would claw back part of the width but cannot turn a +7 % `ADC_TOP`
(10 µm point) into a saving without also moving the strap corridors and
re-closing DRC/LVS/PEX. The bank's empty area is mostly the 7-track routing
channel and the 20 µm row, not width recoverable by fingering.

## Outcome

Null result recorded as a complete outcome (Champion note on #668). Not done,
because there is no folded layout to verify: DRC/LVS of a folded bank, PEX
re-run, and settling / INL-DNL sim rows. The `< 0.1 mm²` target and every
ratified row are unchanged. Other bank levers (channel-track reduction,
different row split of N/P devices) are untested here.
