# ERC record 20261115-021155-784b4d3b

Append-only adjudication record for the `device_body_area_um2` delta that makes
`layout/erc/run_erc.py --check` fail under the `klt` release #652 targets
(`69.2224` reported where `cases.json` expects `16384.0`, for
`cdac_mim_unit_capacitor`). Not minted by the runner: every number below was
re-measured for this record, in throwaway environments, against the same
committed geometry `cases.json` asserts on. A re-run mints its own record; this
one is never edited in place.

- **Record ID** — `20261115-021155-784b4d3b`
- **Claim** — **16384.0 matches the drawn device-body geometry; 69.2224
  measures something else, and the something else is the field's new
  definition.** The field changed meaning upstream between `klt` 0.5.0 and
  0.6.0 (klayout-tools#2226): it used to report the device **marker layer's
  own area**, and now reports the marker **intersected with the declared `on`
  role's own conductor region**. On this layout that is the difference between
  the whole 1024-plate MiM array (16384.0 um^2) and the 1024 Via4 cuts that
  actually land inside it (69.2224 um^2). Neither number indicates a layout or
  extraction-geometry defect; the drawn geometry is exactly the design's
  1024-unit array. Not a tool defect -- the change is documented in upstream's
  `docs/cli/erc.md` -- so nothing is filed.
- **The delta is not new in 0.8.0** — `layout/erc/toolchain.json`'s own
  `_comment` (the "UPDATE (issue #426)" paragraph) already records this exact
  reading under 0.6.0, which is why this flow stayed pinned at
  `0.5.0+g67d617f` while the rest of the repo moved to 0.6.0. Re-measured here:
  0.6.0 and 0.8.0 read identically. What was missing until this record is the
  **adjudication** -- which side is right -- not the observation.
- **Geometry provenance** — `layout/adc-top/adc_block.gds`, top cell
  `ADC_BLOCK`, sha256 `fc10bb2870fed8bc…` (first 16 hex; the full value is
  `cases.json`'s `layout_sha256`, asserted unchanged by every run below).
- **Overall** — ADJUDICATED (delta explained; no re-baseline performed here --
  re-minting `cases.json` expectations is #652's job, which this unblocks)

## What each number measures (derived from drawn geometry, `klayout` 0.30.13)

Flat read of the committed GDS, merged regions, dbu 0.001:

| Region | Measurement |
|---|---|
| `117/10` (MIM_L_MK marker) | 1024 polygons, each exactly 4.0 x 4.0 um -> **16384.0 um^2** |
| `41/0` (Via4) within the marker | 1024 polygons, each exactly 0.26 x 0.26 um -> **69.2224 um^2** |
| `41/0` whole block | 1026 polygons, 69.3576 um^2 (the 2 extra cuts are outside the caps) |
| `110/5` (RES_MK marker) | 2 polygons, **300.0 um^2** |
| `110/5` within `30/0` (Poly2) | **300.0 um^2** (the marker is coincident with the poly body it marks) |

So: **16384.0 is the drawn unit-plate area** -- 1024 unit capacitors x 4.0 um x
4.0 um, exactly the design's array, and exactly what the pinned build reports.
**69.2224 is the carved conductor area on the declared role** -- 1024 Via4 cuts
x 0.26 um x 0.26 um, exactly what the newer build reports. Independent
cross-check that the capacitor bodies really are 4x4: the committed extracted
netlist (`layout/lvs/reports/…/adc_block.extract.spice`) carries 1024
capacitors at 35.6528 fF, i.e. 2.2283 fF/um^2 over 16 um^2 -- the right order
for a gf180mcu MiM.

### Why the resistor did not move (the discriminating observation)

The resistor's 300.0 is unchanged across all three builds because its marker is
coincident with the role layer it carves -- marker area and intersected area
are the same number. **This refutes the "squared unit-conversion factor"
hypothesis** from #798's curation: 69.2224 = 16384.0 x 0.065^2 is exact, but
0.065 = 0.26/4.0 is just this geometry's via-to-plate ratio, so the power is a
coincidence, not a scale factor -- a per-dimension unit bug applied to an area
accumulator would have moved 300.0 to 300.0 x 0.065^2 = 1.2675 too, and it
moved nothing.

### Code-level provenance of the change

- 0.5.0, `klayout_tools/erc.py::_device_body_cuts`:
  `"body_area_um2": round(body.area() * dbu2_um2, 9)` -- the marker's own
  area, though the same function's docstring already called the field "the
  **actual** subtracted area".
- 0.6.0+, `klayout_tools/_devices.py::_device_body_cuts`:
  `subtracted = (body & conductors[role]).merged()` then
  `"body_area_um2": round(subtracted.area() * dbu2_um2, 9)`, with the
  docstring "honest means *intersected* (issue #2226) […] not `area(marker)`".
  Upstream `docs/cli/erc.md` documents the same: "the marker **intersected
  with the `on` role's own conductor region**, issue #2226, not the marker
  layer's own area".

That is also why this is recorded as **not a defect**: the 0.5.0 code already
*documented* the intersected meaning; #2226 made the code match the docs.

## Which side should #652's re-baseline pin

Facts for that decision (the decision itself is #652's):

1. The supply spec's own `_comment` reads the committed 16384.0 as "16384.0
   um^2 **removed from Via4**" -- which was never literally true: only
   69.2224 um^2 of Via4 exists inside the marker. The new semantics is the one
   that makes the spec's own sentence true.
2. `layout/power/cases.json` -- pinned at 0.6.0, same GDS, same `devices[]`
   declarations -- already expects **69.2224** in all 13 of its cases. Two
   flows in this repo currently pin different answers to the same field on the
   same geometry; the post-#2226 value is the one already in live use (see
   #799 for that flow's own 0.8.0 delta).
3. Connectivity is untouched: `erc_status: clean`, identical finding counts,
   at every build measured here.

## Upstream disposition (AC-4)

No tool defect found and no design discrepancy found, so nothing is filed:
the change is intentional, issue-tracked (klayout-tools#2226), and documented
in `docs/cli/erc.md`. Per this issue's framing, filing a bug for documented
intended behaviour would be noise, not signal.
