## Why a fourth record on the same issue

Nothing about this block moved. **`main` advanced past this branch's fork
point a second time while the branch was in review, and it moved
`signoff/gf180-sar-adc.manifest.json` again.**

- `20260921-181434-7bbe8c6` (this branch) carries item 4's `content_hash`
  fix, re-anchored once already against #339's item-8 envelopes. It graded a
  manifest with no item 11 citation at all (`11.analog` renders `unmet` /
  `no_evidence`).
- `20260921-131851-36d405e` (#347/#368, merged to `main` while this branch
  was in review) taught `run_signoff.py` item 11's compound (list-shaped)
  citation shape and cited the `klt erc` supply run. It graded a manifest
  whose `4.analog` was still the bare, unpinned string citation — the exact
  thing this branch exists to fix.

Rebasing this branch onto `main` merges both manifest edits — including
re-pointing item 11's second compound part (`parts[1]`, "the LVS report item
4 grades" per `signoff/gf180-sar-adc.manifest.json`'s own `_comment`) at the
same `content_hash`-bearing LVS report item 4 now cites, so the two rows stay
consistent with each other exactly as the manifest's `_comment` describes.
`run_signoff.py --check`'s step 4b (the "was the report graded on the
citations the manifest names NOW" gate) fails on both `T1#4.analog` and
`T1#11.analog` against the pre-rebase committed report, exactly as designed.
That gate is the reason this record exists — it refused to let a merged
manifest stand on a verdict minted before the merge.

The fix is the one `signoff/README.md` § "Changing the verdict" prescribes
and the only one it allows: re-run `--regen` against the merged manifest and
write a record. **No citation, envelope, artifact hash, or row status was
hand-edited to make `--check` pass.**
